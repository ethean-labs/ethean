# Upstream Refresh Policy

## Goal

This policy keeps Ethean aligned with `leanSpec` main without allowing moving upstream content to alter a frozen implementation phase. A refresh produces evidence and a candidate profile; it never silently mutates the active profile.

## Refresh scope

Every refresh covers:

- `leanSpec` main, release assets, fixture generator, and networking fixtures;
- the current pq-devnet plan, quickstart, test keys, genesis schema, and acceptance criteria;
- selected `leanSig`, `leanVM`, or `leanMultisig` repositories;
- delegated libp2p, Gossipsub, discovery, QUIC, Snappy, and request/response specifications;
- `leanMetrics` when metrics are an acceptance surface;
- all seven peer default branches and their protocol-facing dependency locks;
- open upstream security, correctness, interoperability, and performance work that can invalidate the frozen profile.

Peer refreshes remain evidence refreshes. They do not select values.

## Refresh triggers

Run the workflow:

1. before P0 closes;
2. before every phase freeze;
3. before an interoperability event or release candidate;
4. when `leanSpec` changes a container, constant, transition, fork-choice rule, fixture, node sketch, topic, codec, or test-driver contract;
5. when a selected crypto dependency changes key bytes, signature bytes, parameters, proof statement, serialization, verifier behavior, or security assumptions;
6. when a pq-devnet plan changes generation, fork identity, duties, topology, or acceptance tests;
7. when a security advisory or peer defect indicates a consensus split, proof failure, signature reuse, malformed-input failure, checkpoint weakness, or network wedge;
8. when a fixture asset is replaced, disappears, changes digest, or is generated by a different toolchain.

## Change-diff workflow

### 1. Acquire immutable inputs

- Fetch upstream branches without changing the active profile.
- Resolve every branch and tag to a full commit.
- Download fixture assets once into content-addressed storage.
- Calculate byte length and SHA-256 before extraction.
- Reject redirects to mutable or unauthorized origins.
- Initialize required submodules at recorded gitlinks for inspection.

### 2. Produce a source inventory

For old and candidate commits, inventory:

- consensus type declarations and SSZ bounds;
- fixture manifests, generator dependencies, and skipped/unsupported cases;
- constants and genesis configuration;
- signing and proof APIs;
- state transition, fork choice, finality, and duty scheduling;
- topics, message IDs, compression, request/response, discovery, and ENR fields;
- checkpoint, persistence, and restart contracts;
- compiler, generator, lockfile, submodule, action, and image pins.

### 3. Classify every semantic diff

Assign each change exactly one primary class:

- `consensus`: accepted state or block behavior can change;
- `serialization`: SSZ bytes, roots, bounds, or JSON test-driver contract can change;
- `cryptography`: keys, signatures, proof statements, parameters, or verification can change;
- `network-wire`: topic bytes, message IDs, framing, protocol IDs, response codes, or limits can change;
- `network-policy`: discovery, scoring, rate limits, or peer management changes without changing valid bytes;
- `operator-policy`: checkpoint trust, key custody, storage durability, or deployment changes;
- `toolchain-only`: build output can change without intended protocol behavior;
- `documentation-only`: no executable or generated behavior changes.

If a change could fit a more safety-critical class, use that class until disproven.

### 4. Map diffs to decisions and ledger fields

Every non-documentation diff must identify:

- affected ledger paths;
- affected open decisions;
- owner phase;
- fixture families to regenerate;
- mixed-version failure expectation;
- migration or database impact;
- whether it invalidates the current compatibility fingerprint.

An unclassified changed file in a protocol source, fixture generator, crypto dependency, or network codec closes the gate.

### 5. Regenerate authoritative evidence

Generate fixtures from the candidate source in an exactly pinned environment. Record the command, tool versions, source commit, archive SHA-256, extracted manifest SHA-256, case counts, and crypto scheme.

Compare old and candidate outputs by:

- fixture path additions, removals, and renames;
- canonical SSZ bytes and hash-tree roots;
- accepted/rejected transition results and rejection reasons;
- fork-choice snapshots and tick boundaries;
- signature and proof bytes, sizes, and verification outcomes;
- topic bytes, message-ID preimages/digests, Snappy bytes, and stream frames.

Unknown fixture types and silent skips are failures.

### 6. Differentially test peer evidence

Use at least two current peer implementations where executable support exists. Include all seven in the P4 matrix. A peer result can reveal ambiguity or defects, but cannot override the selected source and fixtures.

Required mixed-version negatives prove that different:

- fork identifiers;
- SSZ schemas;
- crypto generations;
- key/signature sizes;
- proof statements;
- slot timing profiles;
- fixture releases;
- framing rules

fail clearly rather than share a network and fork silently.

### 7. Review security and operations

Explicitly review:

- XMSS duplicate-sign and rollback behavior;
- proof soundness assumptions, Poseidon/Poseidon2 parameter changes, and known native prover failures;
- decode, decompression, allocation, queue, stream, and proof budgets;
- checkpoint trust and canonical-membership evidence;
- database and signer-state migration;
- four-second-slot CPU, memory, deadline, and cancellation behavior;
- moving build inputs and supply-chain changes.

### 8. Create a candidate freeze

Update the compatibility ledger with concrete selected values, compute a new fingerprint, and run the phase's acceptance suite. The active freeze remains unchanged until review accepts the candidate.

## Phase handling

### Between phases

Compatible upstream changes may be accepted through a new freeze. The review must still show why compatibility is preserved and must recompute the fingerprint because source or fixture identity changed.

### During a phase

Queue ordinary upstream changes. Do not rebase protocol behavior mid-phase. A consensus-safety, crypto-safety, or active interop defect pauses the phase and invokes the emergency exception in the authority policy.

### After P4 begins

Any fingerprint change restarts affected P4 fixture, mixed-client, recovery, and long-run evidence. A release candidate cannot inherit results from a different fingerprint.

## Fixture asset policy

Fixture CI must:

1. read the expected URL, length, and SHA-256 from the frozen ledger;
2. download without a `latest` alias;
3. verify digest before extraction;
4. extract into a clean directory;
5. verify the extracted manifest digest and expected case count;
6. fail on unknown types, unsupported operations, duplicate case IDs, missing families, or undeclared skips;
7. retain the asset digest and profile fingerprint in test reports.

Assets generated locally must be packaged and hashed by a reproducible job. A generated tree without an immutable archive digest is not release evidence.

## Required refresh report

Each refresh report must contain:

- old and new commits and asset hashes;
- exact toolchains;
- changed ledger fields;
- semantic diff classification;
- fixture count and byte/root/result changes;
- peer agreements and disagreements;
- security and performance impact;
- decisions opened, resolved, or reopened;
- phase impact;
- resulting candidate fingerprint;
- explicit accept, defer, or reject outcome.

No “no meaningful changes” conclusion is valid without the source inventory and generated-output comparison.

## Fail-closed outcomes

Reject or defer the candidate when:

- an authoritative pin is absent;
- fixture bytes cannot be reproduced;
- a release asset lacks a verified SHA-256;
- crypto and spec revisions are not proven compatible;
- a consensus or wire diff has no fixture;
- a required peer test uses fake or bypassed verification;
- signer or checkpoint safety regresses;
- a moving branch, tag, tool, action, or image remains in the selected build graph;
- the active and candidate profile cannot be distinguished before decoding or signing.
